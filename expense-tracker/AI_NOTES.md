# AI Notes

This project was built with Claude (Anthropic) doing the actual code
generation, from a detailed spec (endpoints, storage constraints, repo
layout, and the "AI_NOTES.md must document usage" requirement itself). Below
is an honest account of what was AI-written, what was checked and how, and
where the AI's first instinct was overridden.

## 1. What was AI-generated vs. hand-written

Everything in `src/` and `tests/` was generated by Claude in a single
session, driven by the assignment brief pasted directly into the prompt.
There is no hand-written code underneath it — it's more accurate to say
the "hand-written" part of this submission was the *review and editing
pass* described below, not a separate authorship layer.

Specifically AI-generated:
- Backend: model/DTO/repository/service/controller/exception classes,
  `pom.xml`, `application.properties`.
- Frontend: all React components, `api.js`, CSS.
- Tests: both `ExpenseServiceTest.java` (unit, fake in-memory repo) and
  `ExpenseControllerTest.java` (MockMvc integration tests).
- `README.md` and this file.

## 2. What was validated, and how (important caveat)

The sandbox this was built in has **no internet access**, so `mvn` and
`npm install` could not actually be run against Maven Central / npm — there
is no way to prove the build is green from inside that environment. What
*was* done automatically, in place of a real build:

- A brace-balance check across every `.java` file (`grep -o '{' ... | wc -l`
  vs. the same for `}`), to catch obvious structural errors.
- `node -e "JSON.parse(...)"` against `package.json` to confirm it's valid
  JSON.
- `node --check` on the plain (non-JSX) JS files (`api.js`, `vite.config.js`)
  to catch syntax errors — JSX files couldn't be checked this way since no
  babel/esbuild toolchain was available offline.
- A manual re-read of every file for the usual AI failure modes: mismatched
  imports, a service method signature that doesn't match how the controller
  calls it, DTO fields that don't line up between request/response.

**Before you submit this, you should actually run it**: `mvn test` from
`src/backend`, then `mvn spring-boot:run` and hit a couple of endpoints with
curl or the Swagger UI, then `npm install && npm run dev` for the frontend.
Treat the code as a strong first draft that has been read carefully but not
compiled — not as something that's been proven to build in a real Maven/npm
environment. If `mvn test` fails, the most likely culprit based on what
Claude flagged as uncertain is the `testSourceDirectory` override in
`pom.xml` (called out below) — worth checking first if tests aren't
discovered at all.

## 3. Specific things checked/changed during the AI-assisted build

- First draft of the JSON persistence used a plain `HashMap` with no
  locking. Changed to a `ReentrantReadWriteLock` around reads/writes once it
  was clear concurrent requests (e.g. add + delete racing) could corrupt the
  on-disk file or leave the in-memory map and file out of sync.
- First draft of the controller test suite reused one running Spring
  context across all test methods without isolating data between them. Since
  adding `@DirtiesContext` per test would make the suite slow for no real
  benefit, each test instead uses a unique category name (e.g.
  `IntegrationTransport`, `IntegrationDelete`) so tests can't collide, and
  the summary test compares a before/after delta instead of an absolute
  total. This is a real tradeoff, not a stylistic one — worth knowing about
  if you add more tests later and reuse a category name.
- The first draft of the controller test helper built the JSON request body
  from a `Map<String, String>`, which would have serialized `amount` as a
  JSON string (e.g. `"9.99"`) rather than a number. Changed it to wrap the
  amount in a `BigDecimal` before serialization so the payload matches what
  a real client would send, instead of relying on Jackson's lenient
  string-to-number coercion to paper over the difference.
- The `pom.xml` remaps `testSourceDirectory` to the top-level `tests/`
  folder instead of using Maven's default `src/test/java`, to satisfy the
  assignment's literal directory layout. This is a nonstandard use of that
  Maven setting — flagging it here because an automated grader unfamiliar
  with the repo might expect tests under `src/backend/src/test/java` and not
  find them there.

## 4. AI suggestions considered and not used

- **Lombok** for the model/DTO classes (`@Data`, `@Getter/@Setter`) to cut
  boilerplate. Rejected: it needs annotation-processor configuration that
  can silently misbehave in some IDE/CI setups, and for a submission that's
  graded on "perfect code" running exactly as documented, plain
  getters/setters are a safer bet than a dependency that could fail
  differently in the grader's environment than in the one it was written in.
- **A Maven wrapper (`mvnw`)** so the grader wouldn't need Maven
  preinstalled. Rejected after checking: generating a real
  `maven-wrapper.jar` requires downloading it, which wasn't possible in this
  offline sandbox, and shipping wrapper *scripts* without a working jar
  would be worse than not shipping them — a broken `./mvnw` is a worse first
  impression than a README that says "you need Maven 3.8+ on your PATH."
- **A local H2/SQLite database** instead of the JSON file. Rejected because
  the assignment explicitly says no database is required and describes JSON
  file storage as an accepted option — adding one would be solving a problem
  that wasn't there.
- **Storing amounts as `double`**. Rejected in favor of `BigDecimal` —
  floating-point rounding on money totals (the summary endpoint sums
  possibly many expenses) is a correctness bug waiting to happen, not a
  style preference.
